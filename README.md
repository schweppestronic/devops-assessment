# DevOps Engineer Homework

Python/Flask config service, packaged in Docker container and deployed in a local Kubernetes (Kubesolo) cluster. Helm handles the application resources, Terraform/OpenTofu drives the deployment, and GitLab CI runs the pipeline.

## User guide

### Prerequisites

- Docker
- A local Kubernetes cluster with the NGINX ingress controller (developed against KubeSolo; kind, minikube, and k3d work too)
- Helm 3
- OpenTofu ≥ 1.6 (or Terraform ≥ 1.5)
- Python 3.12+ (only for running the app and tests without Docker)

### Run the app locally

```bash
cd app
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
pytest
ENVIRONMENT=dev gunicorn -b 0.0.0.0:8080 -w 1 --threads 4 main:app
```

### Build and run the container

```bash
docker build -t homework:1.0.0 app
docker run --rm -p 8080:8080 -e ENVIRONMENT=dev homework:1.0.0
```

### Configuration

The app reads these environment variables:

| Variable      | Default   | Purpose |
| ------------- | --------- | ------- |
| `ENVIRONMENT` | `unknown` | Returned by `GET /env` |
| `APP_VERSION` | `1.0.0`   | Returned by `GET /version`. The image sets it from the `APP_VERSION` build argument; CI passes the commit SHA. |
| `PORT`        | `8080`    | Listening port for both gunicorn and `python main.py`. The image sets it from the `PORT` build argument. If you change it, also change `containerPort` in [helm/values.yaml](helm/values.yaml). |

### Deploy to the cluster

1. Make the image available to the cluster:
   - With a local registry: `docker tag homework:1.0.0 registry.dock/homework:1.0.0 && docker push registry.dock/homework:1.0.0`
   - With kind: `kind load docker-image homework:1.0.0`
   - With minikube: `minikube image load homework:1.0.0`

2. Apply the IaC with tofu (or terraform):

   ```bash
   cd terraform
   tofu init
   tofu apply \
     -var image_repository=registry.dock/homework \
     -var image_tag=1.0.0 \
     -var environment=dev
   ```

   The kubeconfig defaults to `~/.kube/config`; override it with `-var kubeconfig_path=...`.

3. Check the release: `kubectl -n homework get pods,svc,ingress`

### Try it

Using the ingress, after mapping `homework.solo` to the ingress controller IP in `/etc/hosts`:

```bash
curl http://homework.solo/health
```

Without an ingress:

```bash
kubectl -n homework port-forward svc/homework-service 8080:8080
curl localhost:8080/health
curl localhost:8080/version
curl localhost:8080/env
curl -X POST localhost:8080/config -H 'Content-Type: application/json' -d '{"name": "database_url", "value": "postgres://example"}'
curl localhost:8080/config/database_url
curl -X DELETE localhost:8080/config/database_url
```

### API behaviour

- `POST /config` returns `201`. Posting an existing name overwrites it.
- `name` must match `[A-Za-z0-9_.-]{1,128}`, because it is used in the URL path. `value` must be a string of up to 4096 characters. Invalid input returns `400`.
- `GET` and `DELETE` on a missing name return `404` (`DELETE` returns `{"deleted": false}`).
- All errors are JSON: `{"error": "..."}`.
- Config is stored in memory. It is lost on restart and is not shared between pods or gunicorn workers. Keep `-w 1` (threads are safe) and `replicaCount: 1`, or move to a shared store (Redis, a database) to scale out.

### Tear down

```bash
cd terraform && tofu destroy
```

### CI/CD setup (GitLab)

The pipeline is `test → build → deploy`. `test` and `build` run on every branch, while `deploy` only runs on the default branch.

It requires:

- The GitLab container registry enabled on the project (the build job uses the built-in `CI_REGISTRY_*` variables).
- A File-type CI/CD variable `KUBECONFIG` holding the target cluster's kubeconfig.
- A runner that can reach the cluster. For a local cluster, this means a self-hosted runner on the same machine or network; GitLab shared runners cannot reach it.

## What changed

### Application

The app/README.md contained the basic requirements.

- Built the service in Python with Flask and serve it with gunicorn.
- Configured entries are stored in memory meeting the requirements without introducing a database.
- Validated requests: `name` must be URL-safe since it appears in the path, and `value` must be a string within the allowed length. Invalid input returns `400`.
- Errors are returned in JSON format.
- 23 pytest tests cover all endpoints, error cases, and the store's thread safety.

### Container image

- Using `python:3.12-slim` with dependencies declared in `requirements.txt`.
- Runs as non-root user (homework) with UID 10001.
- Runs gunicorn with one worker and four threads allowing concurrent requests.
- `APP_VERSION` and `PORT` build arguments are set as environment variables, so `/version` reports the CI build tag and gunicorn listens on `$PORT`.

### Helm chart

- Renamed the chart from `myapp` to `homework`, then moved names, labels, ports, and image settings into `values.yaml`.
- Templates no longer hard-code environment-specific settings.
- The Service selector `app: myapps` matched no pods, and the Ingress pointed to a non existing `homeworks` Service on port 80.
- Pods, Service, and Ingress now use one label set from values, and the Service targets the container's named `http` port.
- Standardized the ports. The original chart used 8080 for the Service target, and 80 for the Ingress now everything uses 8080.
- Replaced `latest` image tag with the pinned `1.0.0` and added `imagePullPolicy`.
- Added CPU and memory requests and limits.
- Added Pod and container security contexts: `runAsNonRoot` with numeric UID 10001, read-only root filesystem, no privilege escalation, all capabilities dropped, and the `RuntimeDefault` seccomp profile. An in-memory `/tmp` volume keeps gunicorn's worker heartbeat files writable.
- Made the Service and Ingress optional with `service.enabled` and `ingress.enabled`, and set `ingressClassName`.
- Generated [helm/README.md](helm/README.md) with helm-docs.

### Terraform / OpenTofu

The provided configuration was a total disaster, would not even parse: `value =` was empty, `prod` was unquoted, and the `helm` provider block used syntax was removed from  provider version 3.x.

- Pinned the `kubernetes` (`~> 3.4`) and `helm` (`~> 3.3`) providers and committed the lock file, keeping provider versions consistent across runs.
- Switched the deprecated `kubernetes_namespace` resource to `kubernetes_namespace_v1`.
- Revised helm provider 3.x syntax (`kubernetes = {}` plus a `set` list).
- Corrected the chart path from `../helm/homework` to `../helm`.
- Replaced the hard-coded `production` namespace, `prod` environment, and empty image tag with variables -> The chart now receives the image repository, tag, and environment.
- Made the kubeconfig path configurable through `kubeconfig_path`, so CI can use another file.
- Made releases safer to retry: `atomic` rolls back failures, `cleanup_on_fail` removes resources it created, and `timeout` caps the wait at 120 seconds.
- Added a local backend with an explicit state path (`terraform/backend/`) and outputs for the release name, status, revision, and in-cluster endpoint.
- Generated [terraform/README.md](terraform/README.md) with terraform-docs.
- Added Terraform state, plan, variable, and override files to `.gitignore`.

The configuration works with Terraform and OpenTofu. CI uses OpenTofu, so the provider lock file was generated with OpenTofu.

### GitLab CI

The original pipeline had only two jobs for `build` and `deploy` with echoes only so the full CI implementation was neccessary.

- **test:** runs pytest before anything reaches the build stage.
- **build:** uses Docker-in-Docker to build and push an image to the configured registry, tagged with the short commit SHA. Each build has a unique, traceable tag; `latest` obscures the version actually deployed.
- **deploy:** runs `tofu init` and `tofu apply` on the default branch, passing the image and environment as `TF_VAR_*` variables.
- I was considering to implement separated plan and apply jobs in the deploy stage, but dropped the idea since no remote backend is configured and with local the state, each job starts with an empty state file.

## Assumptions

- As specified in the assignment, the target is one local cluster rather than a cloud provider. The defaults (`registry.dock`, `homework.solo`) fit a KubeSolo setup with a local registry and NGINX ingress.
- One `dev` environment is enough to demonstrate the workflow. The `environment` variable allows more to be added later.
- Config entries do not need to survive restarts, so in-memory storage is sufficient.
- The service has no authentication and is assumed to run on a trusted network.
- The deploy job has access to a self-hosted GitLab runner that can reach the cluster.

## Known limitations

- **Terraform state does not persist in CI.** The local backend stores state inside the CI job, then loses it when the job ends. The first deploy succeeds; later ones fail because the namespace already exists. The production improvements describe the fix.
- **Config is lost on restart and not shared.** Each replica or gunicorn worker has its own copy of the in-memory data.
- **No authentication or TLS** for the API or ingress.
- **No linting or security scanning** in CI: no hadolint, tflint, `tofu fmt -check`, `helm lint`, or image scanning.
- **Only one environment.** A second environment would need its own namespace, state, and values.
- The deploy job has no access to any Gitlab runner that can reach my local cluster, this way the CI pipeline was only theoretically tested.

## Production improvements

- **Remote state with locking.** Move the state file to a GitLab-managed HTTP backend or SA/S3/GCS so state survives pipeline runs and concurrent deploys cannot change it together. That also enables a plan job with manual approval before apply.
- **Persistent storage for config.** Use Redis or PostgreSQL for the store. The app can then be stateless and run multiple replicas behind a PodDisruptionBudget and HorizontalPodAutoscaler.
- **Multiple environments.** Give each environment separate namespaces or clusters, state, and values files. Promote from dev to prod through protected branches or release tags, with a manual prod approval.
- **Versioned releases.** Use semantic release versions as image tags and update the chart's `appVersion` to match. Publish the chart to an OCI registry instead of deploying from a local path.
- **Supply-chain security.** Scan images with Trivy, lint the Dockerfile with hadolint and the IaC with tflint and checkov, and sign images with cosign. Build with BuildKit and reuse cached layers to speed builds.
- **Hardening.** Add API authentication, ingress TLS through cert-manager, NetworkPolicies, and a restricted Pod Security Standard.
- **Observability.** Add structured JSON logs, a Prometheus `/metrics` endpoint, and alerts for error rate and latency.
- **GitOps.** For more clusters or teams, let Argo CD or Flux reconcile the chart from Git rather than running Terraform from CI.
